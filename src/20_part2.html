Part 2 — Important Formulas & Rules

Every formula the unit uses, with its variables and a short worked example. Statistics used in the manual problems: EMP = 50,000 tuples / 1,250 blocks / blocking factor 40; DEPT = 10 tuples / 1 block; WORKS = 150,000 tuples / 3,000 blocks; PROJ = 200 tuples.

1.Cost & Cardinality Models

1.1 Block count of a relation

bR = ⌈ nR / bfR ⌉   where   bfR = ⌊ B / tR ⌋

nR = number of tuples · B = block size (bytes) · tR = tuple size (bytes) · bfR = blocking factor (tuples per block) · bR = number of blocks.

Worked example (U3-A-04): B = 4,000 B. EMP tuples are 100 B → bf = ⌊4000/100⌋ = 40, so bEMP = 50,000 / 40 = 1,250 blocks. A projected temp relation of 40 B/tuple → bf = 100 → 50,000/100 = 500 blocks (a saving of 750 blocks, 60 %).

1.2 Selectivity and result cardinality

|result| = nR × s1 × s2 × …   (independent conditions)

si = selectivity (fraction of tuples satisfying condition i).

Worked example (U3-A-03): σsalary>50000(EMP) with s = 0.6 → 50,000 × 0.6 = 30,000 tuples. σcity='Pune'(DEPT) → 2 of 10 → 2 tuples. The join then keeps 30,000 × (2/10) = 6,000 tuples.

1.3 Join cardinality estimate

|R ⋈ S| ≈ ( nR × nS ) / max( V(R,a), V(S,a) )

V(R,a) = number of distinct values of the join attribute a in R.

Worked example (U3-A-05): EMP(50,000) ⋈ WORKS(150,000) on emp_id; each EMP row matches 3 WORKS rows → 50,000 × 3 = 150,000 tuples.

2.Join Algorithms & Index Access Costs

2.1 Block Nested-Loop Join (BNL)

CostBNL = bouter + ⌈ bouter / (M − 2) ⌉ × binner

M = number of buffer pages available · bouter, binner = block counts of the outer and inner relations. The inner relation is re-scanned once per outer chunk of (M−2) blocks, so the smaller relation should normally be the outer one.

Worked example (U3-A-07): M = 52, so M − 2 = 50.
(i) EMP outer: 1,250 + ⌈1250/50⌉ × 3,000 = 1,250 + 25 × 3,000 = 76,250.
(ii) WORKS outer: 3,000 + ⌈3000/50⌉ × 1,250 = 3,000 + 60 × 1,250 = 78,000.
Winner: (i), EMP as the outer relation.

2.2 Index Nested-Loop Join

CostINL = bouter + nouter × ( h + k )

h = height of the index on the inner join attribute · k = block I/Os per matching inner tuple (≈ 1 if unclustered, ≈ 1/bf if clustered).

Worked example (U3-A-07): index height 3, each EMP tuple matches 3 WORKS tuples at 1 I/O each: 1,250 + 50,000 × (3 + 3) = 301,250. It loses to BNL because every outer tuple triggers an index probe on unclustered matches.

2.4 Pushdown savings

Reduction factor = (sum of intermediate sizes, unoptimized) / (sum of intermediate sizes, optimized)
Worked example (U3-A-03): initial tree forms EMP × DEPT = 500,000 tuples before selecting. Optimized tree's intermediates total 30,000 + 2 + 6,000 = 36,002. Comparing the product with the two selected inputs: 500,000 / 30,002 ≈ 16.7× reduction.

3.Schedule Classes & Serializability

3.1 Conflict and conflict equivalence

Rule

Two operations conflict iff they are from different transactions, access the same item, and at least one is a write. Two schedules are conflict equivalent if they order every conflicting pair the same way.

Worked example (U3-C-01): S1 = r1(A) w2(A) r2(B) w1(B) r3(A) w3(B). Conflicting pairs: (r1(A),w2(A)), (w2(A),r3(A)), (r2(B),w1(B)), (r2(B),w3(B)), (w1(B),w3(B)) → 5 pairs. The pair (r1(A),r3(A)) is read/read, so it does not conflict.

3.2 Conflict serializability test

  1. Draw one node per transaction.
  2. For every conflicting pair, add an edge from the earlier transaction to the later one.
  3. Acyclic ⇒ conflict serializable; a topological order is an equivalent serial order.
  4. Cycle ⇒ not conflict serializable.

3.3 View serializability requirements

  • Initial read: if Ti reads the initial value of X in S, it does so in the serial order too.
  • Read-from: if Tj reads a value written by Ti in S, it does so in the serial order too.
  • Final write: the transaction performing the last write of X in S does so in the serial order too.
Worked example (U3-C-05, S5a): r1(A) w2(A) w1(A) w3(A) has the cycle T1→T2→T1, so it is not conflict serializable. View test: r1 reads the initial value (so T1 first) and T3 makes the final write (so T3 last). Only the order T1, T2, T3 satisfies both — it is view serializable.

3.4 Recoverability, cascadelessness, strictness

RecoverableIf Tj reads from Ti, then ci < cj.Find every read-from pair; check commit order.
CascadelessEvery read is of a committed value: no read of an uncommitted write.Every rj(X) must follow the writer's commit.

Worked example (U3-C-07): R2 = w1(A) r2(A) c2 c1 → not recoverable (T2 reads from T1 but c2 precedes c1). R4 = w1(A) w2(A) c1 c2 → recoverable and cascadeless (no reads) but not strict (T2 overwrites T1's uncommitted A).

4.Locking, 2PL & Deadlock

4.1 Lock compatibility

4.2 Two-phase locking rules

  • Growing phase: a transaction may only acquire locks (and may upgrade S → X).
  • Shrinking phase: a transaction may only release locks.
  • Lock point: the instant the transaction holds its final lock, i.e. the boundary between the two phases.
  • Strict 2PL: all exclusive locks are held until commit/abort (shared locks may be released earlier).

4.3 Deadlock detection and prevention

Wait-for edge: Ti → Tj when Ti waits for a lock held by Tj. Deadlock ⇔ cycle.
SchemeOlder requester (TS smaller)Younger requester
Wait-DieWaitsAborts (“dies”)
Wound-WaitWounds — aborts the younger holderWaits

Smaller timestamp = older. Both schemes are deadlock-free because the wait-for graph always points from younger to older.

Worked example (U3-C-14, e1): TS(T1) = 5, TS(T2) = 10, T2 requests a lock held by T1 (younger → older). Wait-Die: T2 aborts. Wound-Wait: T2 waits.

5.Timestamp Ordering & Optimistic Validation

5.1 Basic timestamp ordering (TO)

OperationAbort ifOtherwise
Read(X) by TTS(T) < W-TS(X)Execute; R-TS(X) = max(R-TS(X), TS(T))
Write(X) by TTS(T) < R-TS(X) or TS(T) < W-TS(X)Execute; W-TS(X) = TS(T)

R-TS(X) = largest timestamp of any transaction that read X · W-TS(X) = largest timestamp of any transaction that wrote X. On abort the operations are discarded and timestamps are not restored.

5.2 Thomas Write Rule

Write(X) by T: if TS(T) < R-TS(X) → abort. If R-TS(X) ≤ TS(T) < W-TS(X) → ignore the write. Else execute.
Worked example (U3-C-16, S16a): w2(X) sets W(X) = 2. Then w1(X) with TS = 1: basic TO sees 1 < W = 2 → T1 aborts. Thomas Write Rule: R = 0 ≤ 1 < W = 2 → the write is ignored, T1 continues and both commit. The rule only changes the stale blind-write case.

5.3 Optimistic validation rule

Validation test for Tj against an earlier-validated Ti

Tj passes if finish(Ti) < start(Tj), or both start(Tj) < finish(Ti) < validation(Tj) and WriteSet(Ti) ∩ ReadSet(Tj) = ∅. Any failure ⇒ Tj aborts.

Worked example (U3-C-17, T3 vs T2): finish(T2) = 9, start(T3) = 8, validation(T3) = 10, so 8 < 9 < 10 (overlap). WS(T2) = {C} ∩ RS(T3) = {A,C} = {C} ≠ ∅ → T3 aborts.

6.3 Checkpoint rules

  • A transaction that committed before the checkpoint → IGNORE (already on disk).
  • A transaction in the checkpoint list that commits after it → REDO from its first write.
  • A transaction with an abort record → IGNORE (already rolled back).
  • Scan start = the earliest start record of any transaction active at the checkpoint.

6.4 Shadow paging rules

  • A modified page is copied to the lowest-numbered free location; the current page table is updated.
  • A page modified twice is copied once (the second write is in place).
  • Commit = make the current table the shadow table, then free the replaced locations.
  • Crash before commit = use the shadow table and reclaim all locations allocated by the failed transaction.
Worked example (U3-D-17): shadow table P1→L3, P2→L7, P3→L1, P4→L5, P5→L2; free L4, L6, L8, L9. T modifies P2 then P5 then P2. Current table after T's writes: P1→L3, P2→L4, P3→L1, P4→L5, P5→L6. Crash before commit → database uses the shadow table (P2→L7, P5→L2); L4 and L6 are reclaimed, free list = L4, L6, L8, L9.
