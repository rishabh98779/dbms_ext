B.Transaction Processing

All Section B questions are executable. Run the reset script (UPDATE u3_account …; COMMIT;) before each exercise. Starting balances: 101 = 10000, 102 = 5000, 103 = 20000, 104 = 800.

U3-B-01COMMIT — a multi-row transferL1Executable

Task. Transfer 2,000 from 101 to 102 in one transaction and commit; display all balances.

START TRANSACTION;
UPDATE u3_account SET balance = balance - 2000 WHERE acc_no = 101;
UPDATE u3_account SET balance = balance + 2000 WHERE acc_no = 102;
COMMIT;
SELECT * FROM u3_account;
Expected: 101 = 8000, 102 = 7000, 103 = 20000, 104 = 800. Oracle: identical, minus START TRANSACTION (a transaction begins at the first DML; optionally SET TRANSACTION READ WRITE; first).
U3-B-02ROLLBACK — atomicityL1Executable

Task. Debit 3,000 from 101, SELECT, ROLLBACK, SELECT again.

START TRANSACTION;
UPDATE u3_account SET balance = balance - 3000 WHERE acc_no = 101;
SELECT balance FROM u3_account WHERE acc_no = 101;   -- 7000 inside the transaction
ROLLBACK;
SELECT balance FROM u3_account WHERE acc_no = 101;   -- 10000 after rollback
Oracle note

Same without START TRANSACTION. If a worksheet auto-commits each statement, run the whole sequence as one script or PL/SQL block, otherwise the ROLLBACK has nothing to undo.

U3-B-03SAVEPOINT and partial rollback (with a consistency flaw to spot)L2Executable

Task. In one transaction: debit 101 by 1,000 → SAVEPOINT s1 → credit 102 by 1,000 → SAVEPOINT s2 → debit 103 by 5,000 → ROLLBACK TO s2 → credit 104 by 500 → COMMIT. Then compare the total of all balances.

START TRANSACTION;
UPDATE u3_account SET balance=balance-1000 WHERE acc_no=101;
SAVEPOINT s1;
UPDATE u3_account SET balance=balance+1000 WHERE acc_no=102;
SAVEPOINT s2;
UPDATE u3_account SET balance=balance-5000 WHERE acc_no=103;
ROLLBACK TO SAVEPOINT s2;
UPDATE u3_account SET balance=balance+500  WHERE acc_no=104;
COMMIT;
SELECT *, (SELECT SUM(balance) FROM u3_account) AS total FROM u3_account;
Expected: 101 = 9000, 102 = 6000, 103 = 20000, 104 = 1300. Total 36,300 against 35,800 initially. Flaw: the 500 credit to 104 has no matching debit, so the transaction violates conservation of money. Rolling back to s2 undid only the 103 debit.

Related (U3-B-09, SAVEPOINT name reuse): debit 101 by 1,000 → SAVEPOINT a → credit 102 by 500 → SAVEPOINT a again → credit 103 by 500 → ROLLBACK TO a → COMMIT. Final: 101 = 9000, 102 = 5500, 103 = 20000, 104 = 800. Re-issuing SAVEPOINT a replaces the earlier savepoint of that name in both databases, so only the 103 credit was undone.

U3-B-04ACID — atomicity and consistency through a constraint failureL2Executable

Task. Transfer 1,000 from 104 (balance 800) to 101 by crediting 101 first, then debiting 104. Record the error, inspect the intermediate state, then ROLLBACK.

START TRANSACTION;
UPDATE u3_account SET balance=balance+1000 WHERE acc_no=101;
UPDATE u3_account SET balance=balance-1000 WHERE acc_no=104;   -- fails (balance would be -200)
SELECT acc_no,balance FROM u3_account WHERE acc_no IN (101,104);
ROLLBACK;
SELECT acc_no,balance FROM u3_account WHERE acc_no IN (101,104);

Intermediate11000800Credit still pending; only the failed statement is undone, not the transaction

Error text

MySQL: ERROR 3819 (HY000): Check constraint 'chk_bal' is violated.
Oracle: ORA-02290: check constraint (…CHK_BAL) violated

Related (U3-B-11, bulk update and rollback). Record SUM(salary) for dept_id = 4, then in one transaction give the department a 10 % raise: ROW_COUNT() reports 5,000 rows, and the sum inside the transaction is exactly 1.10 × the original (salaries are whole numbers, so ×1.10 gives exact two-decimal values). After ROLLBACK the sum is back to the original — atomicity across many rows. Oracle reports “5000 rows updated”, or use SQL%ROWCOUNT in a block.

U3-B-06Lost update and row lockingL3Executable

Part 1 — no locks. Both sessions read 101's balance (10000). A writes 9000 and commits; B writes 10500 and commits.

Final 10500 — A's debit is lost, because B overwrote it from a stale read.

Part 2 — with SELECT … FOR UPDATE.

-- A START TRANSACTION; SELECT balance FROM u3_account WHERE acc_no=101 FOR UPDATE;  -- 10000
-- B START TRANSACTION; SELECT balance FROM u3_account WHERE acc_no=101 FOR UPDATE;  -- B BLOCKS
-- A UPDATE u3_account SET balance=balance-1000 WHERE acc_no=101; COMMIT;
-- B -- unblocks, reads 9000
       UPDATE u3_account SET balance=balance+500 WHERE acc_no=101; COMMIT;
Final 9500. B waited for A's exclusive lock. In MySQL, B errors with 1205 if A holds the lock past innodb_lock_wait_timeout (default 50 s). Oracle uses the same syntax and B also waits.
U3-B-07Multi-table transaction with conditional stock deductionL4Executable

Task. Use conditional updates (… AND stock >= qty) and check the affected-row count. Txn 1 orders Laptop ×3 and Mouse ×10; Txn 2 orders Mouse ×5 then Laptop ×3, and rolls back the whole transaction if any line affects 0 rows. Stock starts Laptop = 5, Mouse = 50.

START TRANSACTION;                                    -- Txn 1
UPDATE u3_product SET stock=stock-3  WHERE prod_id=1 AND stock>=3;   -- 1 row
INSERT INTO u3_orders(prod_id,qty) VALUES (1,3);
UPDATE u3_product SET stock=stock-10 WHERE prod_id=2 AND stock>=10;  -- 1 row
INSERT INTO u3_orders(prod_id,qty) VALUES (2,10);
COMMIT;

START TRANSACTION;                                    -- Txn 2
UPDATE u3_product SET stock=stock-5 WHERE prod_id=2 AND stock>=5;    -- 1 row
UPDATE u3_product SET stock=stock-3 WHERE prod_id=1 AND stock>=3;    -- 0 rows (stock = 2)
ROLLBACK;
Expected. After Txn 1: Laptop = 2, Mouse = 40, 2 order rows. After Txn 2: unchanged — the Mouse deduction and its order row were undone together with the failed Laptop line.

Oracle (Txn 2 as PL/SQL): check SQL%ROWCOUNT = 0 after each update and ROLLBACK; RETURN; — same outcome.

U3-B-08Concurrent seat booking — SKIP LOCKED vs NOWAITL5Executable

Problem. Two agents book the first available seat on train 12001 at the same moment. Neither may get the other's seat.

-- MySQL, session A
START TRANSACTION;
SELECT seat_no FROM u3_seat WHERE train_no=12001 AND status='FREE'
  ORDER BY seat_no LIMIT 1 FOR UPDATE SKIP LOCKED;      -- 1
UPDATE u3_seat SET status='BOOKED', passenger='Asha' WHERE train_no=12001 AND seat_no=1;

-- MySQL, session B (before A commits) — skips the locked seat
SELECT seat_no FROM u3_seat WHERE train_no=12001 AND status='FREE'
  ORDER BY seat_no LIMIT 1 FOR UPDATE SKIP LOCKED;      -- 2
UPDATE u3_seat SET status='BOOKED', passenger='Ravi' WHERE train_no=12001 AND seat_no=2;
Expected. seat 1 = Asha, seat 2 = Ravi, seats 3–6 FREE. Without SKIP LOCKED, B's SELECT … FOR UPDATE waits on A's lock on seat 1 until A commits or the 1205 timeout fires.
Why Oracle is different

Oracle does not allow a row-limiting clause together with FOR UPDATE, so there is no direct equivalent of ORDER BY … LIMIT 1 FOR UPDATE SKIP LOCKED. The unit uses a per-seat FOR UPDATE NOWAIT loop instead: A locks seat 1; B's attempt on seat 1 raises ORA-00054: resource busy and acquire with NOWAIT specified, so B falls back to seat 2. A cursor-based FOR UPDATE SKIP LOCKED would lock every free seat when opened, leaving B nothing.

Related (U3-B-12, three-statement atomic transaction). Txn X: Mouse ×4 (price 500) — insert order, decrement stock guarded by stock >= 4, debit 101 by 2,000; commit → Mouse = 46, 1 order row, account 101 = 8,000. Txn Y: Laptop ×1 (price 55,000) — the debit fails with ERROR 3819, so ROLLBACK leaves everything unchanged. The next order_id skips the value consumed by Y's rolled-back insert: AUTO_INCREMENT / identity values are not rolled back, which is not an atomicity failure.

U3-B-10When a transaction really starts — autocommitL2Executable

Task. Test the effect of autocommit on ROLLBACK.

SET autocommit = 1;
UPDATE u3_account SET balance = balance - 1000 WHERE acc_no = 101;
ROLLBACK;
SELECT balance FROM u3_account WHERE acc_no = 101;    -- 9000 (already committed)

SET autocommit = 0;
UPDATE u3_account SET balance = balance - 1000 WHERE acc_no = 101;
ROLLBACK;
SELECT balance FROM u3_account WHERE acc_no = 101;    -- 9000

SET autocommit = 1;
START TRANSACTION;
UPDATE u3_account SET balance = balance - 1000 WHERE acc_no = 101;
ROLLBACK;
SELECT balance FROM u3_account WHERE acc_no = 101;    -- 10000 (rollback worked)
Expected. With autocommit = 1 a lone ROLLBACK does nothing. START TRANSACTION suspends autocommit for that one transaction, so the rollback works. Oracle: SET AUTOCOMMIT ON/OFF — a client feature, not a database one; a browser worksheet's behaviour depends on the tool, so record what yours does.
