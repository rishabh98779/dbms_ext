C.Concurrency Control

Notation: r1(A) T1 reads A · w1(A) T1 writes A · c1 T1 commits · a1 T1 aborts. Schedules read left to right. Neither MySQL nor Oracle lets you configure timestamp ordering, optimistic validation or a precedence-graph checker, so those questions are Manual; I have invented no commands for them.

U3-C-02Precedence graphs and conflict serializabilityL1Manual

Schedules. S2a: r1(A) w1(A) r2(A) w2(A) r1(B) w1(B) r2(B) w2(B). S2b: r1(A) r2(A) w2(A) w1(A).

S2a. On A, w1(A) precedes r2(A) and w2(A) → T1→T2; same on B → T1→T2. The graph is acyclic, so S2a is conflict serializable, equivalent to serial order T1, T2.
S2b. r1(A) before w2(A) → T1→T2; r2(A) before w1(A) → T2→T1. The cycle makes S2b not conflict serializable.

Related (U3-C-03, conflict equivalence). For S3 = w1(A) r2(A) w1(B) r3(B) w2(C) w3(D) the edges are T1→T2 (A) and T1→T3 (B), with T2 and T3 unordered — the serial orders are T1,T2,T3 and T1,T3,T2. For Sx = r1(A) w1(A) r2(A) r1(B) w2(B), the schedule Sy = r1(A) w1(A) r1(B) r2(A) w2(B) keeps both conflicting pairs in the same order, so it is conflict equivalent; Sz = r1(A) r2(A) w2(B) w1(A) r1(B) reverses both pairs (r2(A) before w1(A), w2(B) before r1(B)) and is therefore not equivalent — it matches serial T2,T1 instead.

Related (U3-C-24): for S24 = w1(A) r2(A) w3(B) r4(B) w2(C) r4(C) r1(D) w3(D) the acyclic graph gives serial orders T1,T2,T3,T4 and T1,T3,T2,T4. Appending w2(D) adds T3→T2 and leaves the unique order T1,T3,T2,T4.

U3-C-05View serializability — blind writesL3Manual

Schedules. S5a: r1(A) w2(A) w1(A) w3(A). S5b: w1(A) w2(A) w2(B) w1(B) w3(A) w3(B).

S5a. Conflict test: r1(A) before w2(A) → T1→T2; w2(A) before w1(A) → T2→T1. Cycle → not conflict serializable. View test: r1 reads the initial value (T1 first) and T3 makes the final write (T3 last). Only T1, T2, T3 satisfies both → view serializable.

S5b. Cycle on A → not conflict serializable. There are no reads, and the final writes of A and B are both by T3, so any order with T3 last matches → view serializable as T1,T2,T3 or T2,T1,T3.

Pattern to remember

A schedule that is view serializable but not conflict serializable always owes it to a blind write whose value is overwritten before any read. U3-C-06 gives the negative cases: S6 (r1(A) r2(A) w1(A) w2(A)) and S7 (r1(A) w2(A) r3(A) w1(A)) are neither conflict nor view serializable, because the required order constraints contradict each other. U3-C-25 applies the same reasoning to S25a (not view serializable) and S25b (view serializable only as T1,T2,T3).

Related (U3-C-01, conflicting operations): for S1 = r1(A) w2(A) r2(B) w1(B) r3(A) w3(B) the conflicting pairs are (r1(A),w2(A)), (w2(A),r3(A)), (r2(B),w1(B)), (r2(B),w3(B)) and (w1(B),w3(B)) — 5 pairs. The pair (r1(A),r3(A)) is read/read, so it does not conflict.

U3-C-10Shared and exclusive locks — real lock compatibilityL3Executable

Task (MySQL). A holds FOR SHARE on 101; B takes FOR SHARE (granted at once — S/S compatible). Inspect performance_schema.data_locks, then have B attempt an UPDATE and re-inspect.

SELECT ENGINE_TRANSACTION_ID, OBJECT_NAME, INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_STATUS, LOCK_DATA
FROM performance_schema.data_locks;
Observed. Both transactions hold table-level IS locks plus record-level S,REC_NOT_GAP locks with LOCK_STATUS = GRANTED. After B's update, an extra X,REC_NOT_GAP row for B shows LOCK_STATUS = WAITING. A plain SELECT is a consistent non-locking read and returns immediately. If A had issued an UPDATE instead of committing, the two X-lock upgrades deadlock (error 1213).
Oracle

Oracle row reads take no locks and there is no shared row lock, so the unit uses table locks: LOCK TABLE u3_account IN SHARE MODE; is granted to both sessions, but an UPDATE then waits for A. A lock view (v$lock) needs privileges. If both sessions hold SHARE locks and both try to update, one gets ORA-00060.

Related (U3-C-30, lock waits and timeouts). With A holding a lock on 101: MySQL SET SESSION innodb_lock_wait_timeout = 3; then an UPDATE gives ERROR 1205 after ≈ 3 s; FOR UPDATE NOWAIT gives ERROR 3572; FOR UPDATE SKIP LOCKED returns an empty set. Oracle gives ORA-00054 (NOWAIT), ORA-30006 (WAIT 3) and no rows (SKIP LOCKED). A plain Oracle UPDATE has no default timeout and waits indefinitely. By default (innodb_rollback_on_timeout OFF) a MySQL timeout rolls back only the statement, so B's transaction stays open.

Transactions. T1 = r(A) w(B) w(A) commit. T2 = r(A) w(B) commit (started after T1). Arrival order: r1(A), r2(A), w1(B), w2(B), w1(A). Strict 2PL; upgrades allowed; on deadlock abort the younger and restart it.

#OperationLock requestResult
1r1(A)S(A) by T1Granted

Wait-for graph: T2→T1 and T1→T2 → deadlock. Victim: T2 (younger); it aborts and releases S(A). T1's upgrade is granted, w1(A) runs, T1 commits. T2 restarts: r2(A), w2(B), c2.

Related (U3-C-26, strict 2PL with lock points). T1 = r(A) w(A) r(B) c, T2 = w(B) r(A) c, arrival r1(A), w2(B), r2(A), w1(A), c2, r1(B), c1. T1's upgrade to X(A) is blocked by T2's S(A); c2 releases it, so the executed schedule is r1(A) w2(B) r2(A) c2 w1(A) r1(B) c1 — equivalent to serial T2, T1. Lock points: T2 = S(A), T1 = S(B). The schedule is recoverable, cascadeless and strict, since T1 touches B only after c2.

U3-C-19Real deadlock — DBMS detection (MySQL vs Oracle)L4Executable

Timeline. A debits 101; B debits 102; A debits 102 (blocks); B debits 101 → deadlock.

-- MySQL error in one session:
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
SHOW ENGINE INNODB STATUS\G          -- LATEST DETECTED DEADLOCK section

-- Oracle error after about 3 s:
ORA-00060: deadlock detected while waiting for resource
Corrected solution (the source flags an earlier wording error here).
MySQL (InnoDB): the detector rolls back the entire transaction of the victim; the other session's blocked statement then completes and commits. Both transactions debit 101 and 102 by 100 each, so the committed result is the same whichever session is chosen: 101 = 9900, 102 = 4900.
Oracle: ORA-00060 rolls back only the statement that raised it. That session keeps its earlier update and its lock, so the other session stays blocked until the first ends its transaction. If the erroring session then issues ROLLBACK: 101 = 9900, 102 = 4900. If it issues COMMIT instead: 102 was debited twice and 101 once → 101 = 9900, 102 = 4800.

Prevention. Both sessions update 101 then 102 (ascending account number). The second session simply waits at its first statement and no cycle forms.

U3-C-21Serializability and recoverability together (banking)L5Manual

Scenario. X = 101, Y = 102, Z = 103. T1 moves 101→102, T2 moves 102→103, T3 posts interest to 101 and 103. Operations: r1(X) w1(X) r3(X) w3(X) r2(Y) w2(Y) r1(Y) w1(Y) r2(Z) w2(Z) r3(Z) w3(Z); then c1, c2, c3.

Precedence graph. X: T1→T3. Y: T2→T1. Z: T2→T3. Acyclic → conflict serializable, serial order T2, T1, T3.
Reads-from: T3 reads X from T1; T1 reads Y from T2; T3 reads Z from T2.
Recoverable? No — c1, c2, c3 is wrong: T1 read Y from T2 but commits before T2.
Corrected commit order: c2, c1, c3 (satisfies c2<c1 from T1 reading T2, c1<c3 from T3 reading T1, and c2<c3 from T3 reading T2).
Cascadeless? No — r3(X), r1(Y) and r3(Z) all read uncommitted writes, so an abort of T2 would cascade.
