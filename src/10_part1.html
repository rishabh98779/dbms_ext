Part 1 — Essential Concepts

Plain-language explanations of the four syllabus sections. Each concept is self-contained: you can read this part without opening the original question bank.

A.Query Processing & Optimization

Definition — Query processing

The steps a DBMS performs to turn an SQL statement into a result: parsing → validation → relational-algebra translation → optimization (choose the cheapest plan) → code generation → execution. The optimizer is the part that matters for this unit.

1. Query trees

A query tree (expression tree / evaluation tree) is a diagram of a relational-algebra expression. Leaves are base relations, internal nodes are operators (σ selection, π projection, ⋈ join, × Cartesian product), and the root produces the final result. Data flows bottom-up; each node's output is the next node's input.

The initial (canonical) tree is a literal translation of the SQL: Cartesian products first, then one big selection, then a projection at the top. It is correct but almost never efficient. The optimized tree is the same expression rewritten by heuristic rules so that small intermediate results are produced as early as possible.

2. Heuristic (rule-based) optimization — the standard step sequence

  1. Break up conjunctive selections: σ(c1 ∧ c2) becomes σc1(σc2(R)) — a cascade.
  2. Push selections down the tree as far as the conditions allow (toward the leaves).
  3. Replace Cartesian products + selection by joins: σR.a=S.b(R × S) ⇒ R ⋈a=b S.
  4. Order the joins so the most selective (smallest-result) join runs first.
  5. Push projections down to keep only the attributes needed above (reduces tuple width and block count).
  6. Combine cascaded selections/projections into a single operation where possible.
Key idea

Every heuristic step preserves the result set but changes the cost. The goal is always the same: make the intermediate relations as small as possible as early as possible.

3. Which conditions can be pushed where

Condition typeExampleCan be pushed?
Single-relatione.dept_id = 3Yes — push onto that relation's leaf.
Join conditione.emp_id = w.emp_idYes — becomes the join predicate.
Mixed (spans two relations, non-equality)w.hours*400 > e.salaryNo — applied immediately after the join.

Missing this distinction is a classic exam error: a mixed condition cannot be pushed below the join that supplies both of its relations.

4. Cost-based optimization

When several equivalent plans survive the heuristics, the optimizer estimates each plan's cost using catalog statistics (tuple counts, block counts, blocking factor, index heights, distinct values) and picks the cheapest. Cost is usually measured in block (page) I/O, sometimes with CPU cost added.

Definition — Selectivity

Selectivity = the fraction of tuples that satisfy a predicate. A predicate with selectivity 0.1 keeps 10 % of the rows. The result cardinality = (input tuples) × (selectivity). With several independent conditions, multiply the selectivities.

5. Access paths and indexes

For a single-table selection the optimizer chooses between:

  • Linear (full) scan — read every block of the relation.
  • Clustered index — records of a key value are stored physically together, so a range reads few blocks.
  • Secondary (unclustered) index — each matching record can sit in a different block: roughly one I/O per record.
  • Covering index — the index alone holds all needed columns, so the table is never touched.

A sargable predicate lets the index be used for a range seek. Wrapping the indexed column in a function (DATE_FORMAT(hire_date,...), TO_CHAR(...)) destroys sargability and forces a scan — the classic slow-report bug.

6. Join ordering

Joins are commutative and associative, so the same query has many join orders. The optimizer estimates each order's intermediate sizes and picks the one with the smallest total. A plan that forms a Cartesian product early is almost always the worst.

B.Transaction Processing

Definition — Transaction

A transaction is a logical unit of work: a sequence of operations that must be treated as a single, indivisible action. It ends with COMMIT (make permanent) or ROLLBACK (undo everything).

1. The ACID properties

PropertyMeaningHow the unit demonstrates it
AtomicityAll operations happen, or none do.A failed debit triggers ROLLBACK; a transfer never half-completes.
ConsistencyA transaction moves the database from one valid state to another.A CHECK constraint rejects a negative balance.
IsolationConcurrent transactions do not see each other's partial work.Two-session exercises: snapshots, dirty reads, lost updates.
DurabilityCommitted changes survive a crash.Write-ahead logging; REDO of committed work.

2. Transaction control statements

  • START TRANSACTION (MySQL) / first DML (Oracle) — begins a transaction.
  • COMMIT — makes all changes permanent and releases locks.
  • ROLLBACK — undoes all changes since the transaction began.
  • SAVEPOINT name / ROLLBACK TO SAVEPOINT name — partial rollback: undo only back to the marker.
Trap — DDL commits implicitly

In both MySQL and Oracle, a DDL statement (CREATE, ALTER, DROP) commits the current transaction implicitly. A later ROLLBACK has nothing left to undo. This is why “I rolled back but the change stayed” happens after an ALTER.

Definitions — the three anomalies
  • Dirty read — reading data written by another transaction that has not yet committed.
  • Non-repeatable read — the same row returns different values when read twice in one transaction.
  • Phantom — re-running the same query returns new rows inserted by another transaction.

4. The lost-update problem

Two transactions read the same value, each computes a new value from it, and both write back. The second write overwrites the first, so one update is lost. The cure is to lock the row while it is read: SELECT ... FOR UPDATE (exclusive) so the second transaction blocks until the first commits.

5. Autocommit

When autocommit = 1 (MySQL default), every statement commits immediately, so a lone ROLLBACK does nothing. START TRANSACTION suspends autocommit for the duration of that one transaction, which is why the rollback then works. Oracle's SET AUTOCOMMIT ON/OFF is a client setting, not a database one.

C.Concurrency Control

1. Schedules and notation

A schedule is an interleaving of the operations of several transactions, read left to right in time order. Notation: r1(A) = T1 reads A; w1(A) = T1 writes A; c1 = T1 commits; a1 = T1 aborts. Two operations conflict if they belong to different transactions, access the same item, and at least one is a write. Read/read pairs never conflict.

2. Conflict serializability and precedence graphs

Build a precedence graph: a node per transaction, and an edge Ti → Tj whenever an operation of Ti precedes a conflicting operation of Tj. The schedule is conflict serializable iff the graph is acyclic. A topological order of the graph is an equivalent serial order.

Definition — View serializability

A schedule is view serializable if it is view-equivalent to some serial schedule: the same transaction reads each item's initial value, every read reads from the same write, and the same transaction performs each item's final write. Every conflict-serializable schedule is view serializable, but not the reverse — the gap is closed by blind writes (a write not preceded by a read of that item in the same transaction).

3. Recoverability classes

Strict ⇒ cascadeless ⇒ recoverable. The implications do not run the other way.

4. Lock-based concurrency control

  • Shared lock S(X) — read access; several transactions may hold S on the same item.
  • Exclusive lock X(X) — write access; held by exactly one transaction.
  • Compatibility: S/S compatible; S/X and X/X conflict. A conflicting request blocks.

5. Two-phase locking (2PL)

A transaction has a growing phase (only acquiring locks) and a shrinking phase (only releasing). The moment it holds all its locks and begins releasing is the lock point. Plain 2PL guarantees conflict serializability but not recoverability. Strict 2PL holds all exclusive locks until commit/abort — that guarantees both serializability and strictness, and is what real engines implement.

Trap — 2PL vs strict 2PL

A transaction that releases a lock before commit satisfies 2PL but not strict 2PL (e.g. X(A) … U(A) … c). Releasing a shared lock early is allowed by both; releasing an exclusive lock early breaks strictness only.

6. Deadlock

A deadlock is a cycle in the wait-for graph (edge Ti → Tj when Ti waits for a lock held by Tj). Handled by:

  • Detection + recovery — detect the cycle and abort a victim (usually the youngest, or the lowest rollback cost).
  • Prevention by timestamp — Wait-Die: older requester waits, younger requester dies. Wound-Wait: older requester wounds (aborts) the younger holder, younger requester waits.
  • Timeout — a blocked request gives up after a fixed wait (MySQL innodb_lock_wait_timeout).

7. Timestamp ordering (TO)

Each transaction gets a timestamp TS(T). Each item X keeps R-TS(X) (largest timestamp of a reader) and W-TS(X) (largest timestamp of a writer). Operations run only if they arrive in timestamp order; otherwise the transaction aborts and restarts with a new timestamp. No locks, so no deadlock — but possibly many restarts.

Thomas Write Rule

A refinement: if TS(T) < W-TS(X) but TS(T) ≥ R-TS(X), the write is obsolete — ignore it and continue instead of aborting. It changes only the stale blind-write case and makes some non-serializable schedules acceptable.

8. Optimistic concurrency control (validation)

Transactions run freely in a read phase, then pass a validation phase before writing. Each transaction has a ReadSet and WriteSet. Tj validates against every earlier-validated Ti: it passes if either finish(Ti) < start(Tj), or start(Tj) < finish(Ti) < validation(Tj) and WriteSet(Ti) ∩ ReadSet(Tj) = ∅. Otherwise it aborts.

D.Database Recovery

1. Failures

  • Transaction failure — a bad statement or explicit ROLLBACK. The engine undoes the transaction; the database stays available.
  • System failure (crash) — power loss or software crash. Volatile memory is lost; the log on disk survives.
  • Media failure — disk damage; needs a backup restore plus log replay.

2. The log and write-ahead logging

A log is an append-only record of every change. Write-ahead logging (WAL) is the rule that the log record for a change must reach stable storage before the changed page is written to disk. This is what makes recovery possible: the log can always reconstruct or undo a change.

The two recovery passes (immediate modification)

Pass 1 — UNDO: scan the log backward; for every transaction with a start but no commit/abort, restore each item's old value. Pass 2 — REDO: scan forward; for every committed transaction, re-apply each new value in log order. UNDO must go backward so the earliest old value wins.

4. Checkpoints

At a checkpoint, all log records and all modified pages are forced to disk. Benefits:

  • A transaction that committed before the checkpoint needs no recovery action.
  • Recovery only has to scan the log from the earliest start of a transaction active at the checkpoint onward.
  • Under deferred modification, a transaction active at the checkpoint that later commits must still be redone from its first write, because nothing of it was on disk.

5. Shadow paging

The database keeps two page tables: the current table (for the active transaction) and the shadow table (the committed state). A modified page is copied to a new location, and the current table is updated. Commit makes the current table the shadow table (one atomic pointer switch). A crash before commit simply discards the current table — no undo is needed. The cost is that committed data ends up scattered and needs periodic garbage collection.

Trap — recovery order and direction
  • UNDO is always backward (latest log entry first). Running it forward leaves the wrong value.
  • REDO is always forward in log order, so the last write to an item wins.
  • A transaction with an abort record is already complete: neither undo nor redo it.
  • UNDO and REDO write absolute values, so repeating them is harmless (idempotent).
