U3-A-01Query trees, SQL → relational algebra, selection cascadeL1Manual

Problem. For SELECT emp_name FROM u3_emp WHERE dept_id = 3 AND salary > 90000; write the RA expression, draw the canonical tree, and rewrite the selection as a cascade in both orders.

Solution.

RA:      π_emp_name( σ_(dept_id=3 ∧ salary>90000)(EMP) )
Cascade 1: π_emp_name( σ_dept_id=3( σ_salary>90000(EMP) ) )
Cascade 2: π_emp_name( σ_salary>90000( σ_dept_id=3(EMP) ) )

Canonical tree — one conjunctive selection above the leaf:

      π emp_name
          |
   σ dept_id=3 ∧ salary>90000
          |
         EMP

Both cascades are equivalent to the conjunctive selection (rule: σc1∧c2 ≡ σc1 ∘ σc2, and the two single-condition selections commute). In each cascade tree the two σ nodes are simply stacked in the order listed.

For the two-table join on dept_id: MySQL already has the FK index fk_emp_dept, so u3_dept usually drives and u3_emp is accessed by ref; with IGNORE INDEX (fk_emp_dept) it falls to a full scan with a join buffer (hash join in 8.0.18+). Problem. SELECT e.emp_name, d.dept_name FROM u3_emp e, u3_dept d WHERE e.dept_id=d.dept_id AND d.city='Pune' AND e.salary>50000; 2 of 10 departments are in Pune; selectivity of salary>50000 is 0.6. Compute the tuples at every node in the initial and the optimized tree, then the reduction.

Initial tree (Cartesian product first)Tuples
EMP × DEPT50,000 × 10 = 500,000
after all selections50,000 × 0.2 × 0.6 = 6,000
Optimized tree (selection pushed down)Tuples
σsalary>50000(EMP)50,000 × 0.6 = 30,000
σcity='Pune'(DEPT)2
Join30,000 × (2/10) = 6,000
Expected. Initial intermediates ≈ 500,000 (+6,000); optimized 30,000 + 2 + 6,000 = 36,002. Comparing the product with the two selected inputs: 500,000 / 30,002 ≈ 16.7× reduction.

Related (U3-A-16 — classifying conditions). For SELECT e.emp_name FROM EMP e, WORKS w WHERE e.emp_id=w.emp_id AND e.salary>50000 AND e.dept_id=3 AND w.hours>100 AND w.hours*400 > e.salary: e.salary>50000 and e.dept_id=3 are single-relation (EMP), w.hours>100 is single-relation (WORKS), e.emp_id=w.emp_id is the join condition, and w.hours*400 > e.salary is mixed — it cannot be pushed below the join and is applied immediately after it. Optimized sizes: σ_EMP = 50,000 × 0.6 × 0.1 = 3,000; σ_WORKS = 150,000 × 0.2 = 30,000; join = 30,000 × (3,000/50,000) = 1,800; after the mixed condition = 900. The initial tree must first form a 7.5-billion-tuple product. Leaves kept — EMP: emp_id, emp_name, salary; WORKS: emp_id, hours.

U3-A-04Projection pushdown and block estimatesL2Manual

Problem. For πemp_name( EMP ⋈ σcity='Pune'(DEPT) ): pushing the projection onto EMP produces a temp relation (emp_name, dept_id) of 40 B/tuple; the final result tuple is 30 B; the join result is 10,000 tuples. Compute the blocks of EMP, the temp relation and the output.

EMP            : bf = ⌊4000/100⌋ = 40   → 50,000 / 40  = 1,250 blocks
Projected temp : bf = ⌊4000/40⌋  = 100  → 50,000 / 100 =   500 blocks
Final output   : bf = ⌊4000/30⌋  = 133  → ⌈10,000/133⌉ =    76 blocks
Expected. The projection cuts the join's EMP input from 1,250 to 500 blocks — a saving of 750 blocks (60 %).

Problem. EMP ⋈ WORKS ⋈ σloc='Delhi'(PROJ), with 20 of 200 projects in Delhi. Compute each plan's intermediate sizes and rank them.

PlanFirst intermediateSecondSum
A: (EMP ⋈ WORKS) ⋈ σPROJ150,000150,000 × (20/200) = 15,000165,000

Related (U3-A-11 — three-way query). For SELECT p.pname FROM PROJ p, WORKS w, EMP e WHERE p.proj_id=w.proj_id AND w.emp_id=e.emp_id AND e.dept_id=3 AND p.loc='Delhi' (dept_id=3 keeps 1/10 of EMP; 20 of 200 projects are in Delhi), the optimized tree is π_pname( (π(σ_loc='Delhi'(PROJ)) ⋈_proj_id π(WORKS)) ⋈_emp_id π(σ_dept_id=3(EMP)) ). Projection lists — PROJ: proj_id, pname · WORKS: emp_id, proj_id · EMP: emp_id. Intermediate sums: (σPROJ ⋈ WORKS) ⋈ σEMP = 15,000 + 1,500 = 16,500; (σEMP ⋈ WORKS) ⋈ σPROJ = 16,500 (a tie); the Cartesian-first plan = 100,000 + 1,500 = 101,500, about 6× worse.

U3-A-07Cost-based optimization — BNL vs index nested loopL3Manual

Problem. Cost EMP ⋈ WORKS on emp_id with M = 52 buffer pages. BNL cost = bouter + ⌈bouter/(M−2)⌉ × binner. A secondary B+ tree on WORKS.emp_id has height 3; each EMP tuple matches 3 WORKS tuples at 1 block I/O per matching tuple. Compare BNL (EMP outer), BNL (WORKS outer) and index nested loop (EMP outer).

(i)  EMP outer   : 1,250 + ⌈1250/50⌉ × 3,000 = 1,250 + 25 × 3,000 =  76,250
(ii) WORKS outer : 3,000 + ⌈3000/50⌉ × 1,250 = 3,000 + 60 × 1,250 =  78,000
(iii) Index NL   : 1,250 + 50,000 × (3 + 3)                       = 301,250
Best is (i) — BNL with EMP as the outer relation. Index nested loop loses because every EMP tuple triggers a probe and the matches are unclustered.

Related: U3-A-12 uses the same BNL formula (M = 12) to compare pushdown with a temp relation (best: 40,500) against no pushdown (376,250) — a ≈ 9.3× ratio.

U3-A-08Access-path selection and break-even pointL4Manual

Problem. SELECT * FROM EMP WHERE dept_id = 3; returns 5,000 tuples. Three candidate paths: linear scan; secondary (unclustered) B+ tree of height 3 at 1 I/O per record; clustered B+ tree of height 3 with contiguous records. Rank them and find the break-even record count.

Linear scan      : 1,250
Secondary index  : 3 + 5,000          = 5,003
Clustered index  : 3 + ⌈5000/40⌉ = 128
Ranking: clustered (128) < scan (1,250) < secondary (5,003). Break-even: 3 + r = 1,250 → r = 1,247 records. Above that, the linear scan beats the secondary index.
U3-A-09Composite index design — column order mattersL4Executable

Problem. For SELECT COUNT(*) FROM u3_emp WHERE dept_id=3 AND salary BETWEEN 90000 AND 99999; create idx_ds(dept_id, salary) and idx_sd(salary, dept_id), force each in turn, and name the better index.

-- MySQL (Oracle uses /*+ INDEX(e idx_ds) */ hints)
EXPLAIN SELECT COUNT(*) FROM u3_emp USE INDEX (idx_ds) WHERE dept_id=3 AND salary BETWEEN 90000 AND 99999;
EXPLAIN SELECT COUNT(*) FROM u3_emp USE INDEX (idx_sd) WHERE dept_id=3 AND salary BETWEEN 90000 AND 99999;
Verdict: idx_ds.

Related (U3-A-13, subquery vs join). WHERE dept_id IN (SELECT dept_id FROM u3_dept WHERE city='Delhi') and the equivalent join are usually rewritten to the same semijoin by a modern optimizer (MySQL and Oracle both unnest the IN subquery), so the plans are often identical. Delhi holds 3 of 10 departments, so a hash join or a join-buffered scan on EMP is plausible. This is version- and statistics-dependent — record what you observe rather than assuming.

 Equality on the leading column plus a range on the second narrows the index range directly (estimated rows ≈ 5,000 × 12.5 % ≈ 600). idx_sd scans the whole salary range (≈ 6,000 entries) and filters dept_id inside the index — about 10× more entries touched. Both are covering for COUNT(*). Estimates are statistics-dependent.

Related (U3-A-14): with idx_ds forced, SELECT dept_id, salary … is answered from the index alone (MySQL Using index; Oracle shows only the INDEX RANGE SCAN), while SELECT emp_name … needs table row lookups (Oracle adds TABLE ACCESS BY INDEX ROWID).

U3-A-10Query rewriting and sargability (real-world slow report)L5Executable

Problem. An HR report on March-2016 hires is slow. Index hire_date, then compare the original function-wrapped predicate with a half-open range rewrite.

-- original (not sargable: the column is wrapped in a function)
MySQL : WHERE DATE_FORMAT(hire_date,'%Y-%m') = '2016-03'
Oracle: WHERE TO_CHAR(hire_date,'YYYY-MM')   = '2016-03'
-- rewrite (sargable: half-open date range)
MySQL : WHERE hire_date >= '2016-03-01' AND hire_date < '2016-04-01'
Oracle: WHERE hire_date >= DATE '2016-03-01' AND hire_date < DATE '2016-04-01'
Original: full scan (or full index scan), ≈ 50,000 estimated rows — the index cannot be range-seeked. Rewrite: MySQL type = range, key = idx_hire, ≈ 500 rows; Oracle INDEX RANGE SCAN IDX_HIRE. The ≈ 1.03 % follows from 31 of 3,000 days.

Optimized tree:
π_pname( ( π_(proj_id,pname)(σ_loc='Delhi'(PROJ)) ⋈_proj_id π_(emp_id,proj_id)(WORKS) )
            ⋈_emp_id π_emp_id(σ_dept_id=3(EMP)) )

U3-A-15Index effect on ORDER BY / top-N queriesL2Executable

Problem. Run EXPLAIN for the top-10 salaries, create idx_sal(salary), and repeat.

EXPLAIN SELECT emp_id, salary FROM u3_emp ORDER BY salary DESC LIMIT 10;   -- MySQL
CREATE INDEX idx_sal ON u3_emp(salary);
EXPLAIN SELECT emp_id, salary FROM u3_emp ORDER BY salary DESC LIMIT 10;

-- Oracle (12c+): WHERE salary IS NOT NULL is required, see below
EXPLAIN PLAN FOR SELECT emp_id, salary FROM u3_emp WHERE salary IS NOT NULL
                 ORDER BY salary DESC FETCH FIRST 10 ROWS ONLY;
RunMySQLOracle
Beforetype = ALL, Extra: Using filesort, rows ≈ 50,000TABLE ACCESS FULL + SORT ORDER BY STOPKEY
Aftertype = index, key = idx_sal, Extra: Backward index scantypically INDEX FULL SCAN DESCENDING IDX_SAL + COUNT STOPKEY (no sort)
Why Oracle needs IS NOT NULL

Oracle B-tree indexes do not store rows whose indexed key is entirely NULL. salary is nullable, so without the predicate Oracle cannot use the index to return all rows in order. MySQL has no such restriction. Oracle's choice is still cost-based — confirm it in your output.
