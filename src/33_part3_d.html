D.Database Recovery

Neither MySQL nor Oracle lets you switch on deferred modification, shadow paging or a manual UNDO/REDO pass. Questions D-01 to D-04 and D-23 are Executable (real transaction failure and rollback); D-05 onwards are Manual paper simulations of the recovery algorithms. Log notation is in Part 1 §D.2. Initial values are given in each question.

D.1 — Executable: transaction failure and rollback

U3-D-01Statement-level UNDO after a constraint failureL2Executable
UPDATE u3_account SET balance = balance - 1000;   -- ERROR 3819: Check constraint 'chk_bal' is violated.
SELECT * FROM u3_account;                          -- 10000, 5000, 20000, 800 (nothing changed)

START TRANSACTION;
UPDATE u3_account SET balance = balance - 100 WHERE acc_no = 101;
UPDATE u3_account SET balance = balance - 1000;                 -- fails again
SELECT * FROM u3_account;                          -- 101 = 9900, others unchanged
ROLLBACK;
SELECT * FROM u3_account;                          -- 101 = 10000
Expected. The failed multi-row statement is undone as a unit, including rows changed before 104 failed. The earlier 100 debit survives because only the statement was rolled back, not the transaction — the final ROLLBACK/COMMIT decides its fate. Oracle: same statements, error ORA-02290: check constraint (…CHK_BAL) violated.
U3-D-02Limits of ROLLBACK — implicit commit by DDLL2Executable
START TRANSACTION;                                    -- Oracle: omit
UPDATE u3_account SET balance = balance - 100 WHERE acc_no = 101;
CREATE TABLE u3_tmp (x INT);                          -- Oracle: x NUMBER
ROLLBACK;
SELECT balance FROM u3_account WHERE acc_no = 101;    -- 9900, NOT 10000
Expected: 9900. DDL commits the open transaction implicitly in both databases, so the debit was already committed before ROLLBACK, which then had nothing to undo. Clean up with DROP TABLE u3_tmp; and restore 101 to 10,000.
U3-D-03Abrupt termination — where MySQL and Oracle differL3Executable

MySQL. A begins and debits 101 by 500. B runs KILL <A's connection id>;. Then B reads 101 and debits it by 100; A runs any statement.

SELECT balance FROM u3_account WHERE acc_no = 101;                 -- 10000
UPDATE u3_account SET balance = balance - 100 WHERE acc_no = 101;  -- does not block (once rollback finishes)
-- A: SELECT 1;  -- error such as 2006 "server has gone away" or 2013 "Lost connection"

Oracle. Debit 101 by 500 (uncommitted), then run an anonymous block that debits 102 by 100 and then debits 104 by 1,000 (violating chk_bal) with no exception handler.

SELECT acc_no, balance FROM u3_account WHERE acc_no IN (101,102);  -- 9500, 5000
ROLLBACK;
SELECT acc_no, balance FROM u3_account WHERE acc_no IN (101,102);  -- 10000, 5000
Key difference. MySQL's KILL rolls back the entire transaction of the killed session, so B reads 10000. In Oracle the failed block's own changes (the 102 debit) are undone, while the earlier statement outside the block stays pending until your ROLLBACK. Error text: ORA-02290 (shown with ORA-06512 for the block).
U3-D-04Observing write-ahead log activityL2Executable
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';        -- 1 by default
SHOW ENGINE INNODB STATUS\G                                  -- LOG section: Log sequence number N1
UPDATE u3_account SET balance = balance - 1 WHERE acc_no = 101; COMMIT;
SHOW ENGINE INNODB STATUS\G                                  -- N2 > N1
START TRANSACTION; UPDATE u3_account SET balance = balance - 1 WHERE acc_no = 101; ROLLBACK;
SHOW ENGINE INNODB STATUS\G                                  -- N3 ≥ N2
Expected. The flush variable is 1 and the log sequence number increases after the commit. After a rolled-back change it normally still increases, because InnoDB logs the change and its undo. Oracle: SELECT acc_no, balance, ORA_ROWSCN FROM u3_account; — ORA_ROWSCN for the block holding 101 is larger after the commit. By default it has block-level granularity, so rows in the same block may share a value. V$LOG views need privileges and are omitted.

U3-D-05 · U3-D-06Deferred vs immediate modification — the two basic drillsL1Manual

U3-D-05 (deferred, REDO only). Initial A=100, B=200, C=300.

1 <T1,start>   2 <T1,A,150>   3 <T2,start>
4 <T2,B,250>   5 <T1,commit>  6 <T2,C,350>   CRASH

UNDO list: T2. REDO list: T1. UNDO backward: entry 6 → C = 300; entry 5 → B = 200. REDO forward: entry 2 → A = 150. Final: A = 150, B = 200, C = 300.

1 <T1,start>  2 <T1,A,100,150>  3 <T1,commit>  4 <T2,start>  5 <T2,B,200,250>  6 <T3,start>  7 <T3,C,300,350>

Related (U3-D-26, why UNDO must run backward). Initial A=1, B=5, C=9, D=0. UNDO: T1, T3; REDO: T2. Undo backward — entry 9 → D = 0, entry 6 → A = 2, entry 3 → B = 5, entry 2 → A = 1; redo entry 5 → C = 8 → A = 1, B = 5, C = 8, D = 0. Run forward instead and entry 6 would set A = 2 after entry 2 set A = 1, leaving A = 2 — wrong, since A was originally 1. The earliest old value must win.

U3-D-23Month-end fee batch with per-account SAVEPOINTs (real-world)L5Executable

A fee of 900 is charged to each of 101, 102, 103, 104. Each posting is two statements: insert into u3_fee_log, then debit the account. A failed posting must be fully undone without losing the others.

START TRANSACTION;
SAVEPOINT sp_101;
INSERT INTO u3_fee_log VALUES (101, 900);
UPDATE u3_account SET balance = balance - 900 WHERE acc_no = 101;   -- ok

SAVEPOINT sp_102;
INSERT INTO u3_fee_log VALUES (102, 900);
UPDATE u3_account SET balance = balance - 900 WHERE acc_no = 102;   -- ok

SAVEPOINT sp_103;
INSERT INTO u3_fee_log VALUES (103, 900);
UPDATE u3_account SET balance = balance - 900 WHERE acc_no = 103;   -- ok

SAVEPOINT sp_104;
INSERT INTO u3_fee_log VALUES (104, 900);                           -- ok
UPDATE u3_account SET balance = balance - 900 WHERE acc_no = 104;
-- ERROR 3819: Check constraint 'chk_bal' is violated.
ROLLBACK TO SAVEPOINT sp_104;      -- removes the log row for 104
COMMIT;
Expected. Fee-log rows for 101, 102 and 103 only; balances 9100, 4100, 19100, 800. The failed posting for 104 is the only thing undone. The ROLLBACK TO is what removes 104's log row, because the failed UPDATE rolled back only its own statement.
Oracle: one anonymous block looping over the accounts with an inner BEGIN … EXCEPTION WHEN OTHERS THEN ROLLBACK TO sp_posting; END;. Re-issuing SAVEPOINT sp_posting moves the earlier savepoint of that name, which is why the loop works.
U3-D-25Shadow paging — crash during the commit sequenceL4Manual

Committed table: P1→L1 (10), P2→L2 (20), P3→L3 (30). T sets P1 = 11 (copied to L4) and P2 = 21 (copied to L5). Commit has three steps: (1) write the current page table to disk, (2) update the root pointer to the new table, (3) free the old locations L1 and L2.

Crash pointState after restartUnreachable locations
(i) before step 1P1→L1=10, P2→L2=20, P3→L3=30L4, L5 (reclaimed)
(ii) after step 1, before step 2same as (i) — the root still points to the old tableL4, L5 (the new table on disk is unused)
(iii) after step 2, before step 3P1→L4=11, P2→L5=21, P3→L3=30L1, L2 (garbage not on the free list)
Recovery rule: the database uses whichever page table the root pointer designates. Atomicity follows from step 2 being a single pointer write — the transaction is either entirely visible or entirely absent. In case (iii) a restart scan (or garbage collection) finds the locations not referenced by the active table and frees them.
