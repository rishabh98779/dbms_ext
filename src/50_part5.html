1.Ten Definitions You Must Be Able to State

TermOne-line definition
Query treeA diagram of a relational-algebra expression: leaves are relations, internal nodes are operators, the root is the result.
SelectivityThe fraction of tuples satisfying a predicate; result size = input tuples × selectivity.
TransactionA logical unit of work that is either entirely committed or entirely rolled back.
ACIDAtomicity, Consistency, Isolation, Durability.
ConflictTwo operations on the same item from different transactions where at least one is a write.
Conflict serializableThe precedence graph is acyclic.
RecoverableIf Tj reads from Ti, then Ti commits before Tj.
Strict 2PLAll exclusive locks are held until commit/abort — gives serializability and strictness.
Write-ahead loggingThe log record for a change reaches stable storage before the changed page does.
CheckpointA point where all log records and modified pages are forced to disk, bounding how far recovery must scan.

3.Differences That Are Easy to Mix Up

PairDistinction
2PL vs Strict 2PL2PL releases locks in a shrinking phase; strict 2PL holds every exclusive lock until commit.
Conflict vs view serializabilityConflict uses the acyclic precedence graph; view uses initial reads, read-from and final writes. View serializable but not conflict serializable happens only with blind writes.
Recoverable vs cascadelessRecoverable just orders the commits; cascadeless forbids reading any uncommitted value, so no cascade can start.
Wait-Die vs Wound-WaitWait-Die: older waits, younger dies. Wound-Wait: older wounds the younger holder, younger waits.
Basic TO vs Thomas Write RuleThomas ignores a stale blind write instead of aborting; the read rule is unchanged.
UNDO vs REDOUNDO (backward) restores old values of uncommitted transactions; REDO (forward) re-applies new values of committed ones.
Deferred vs immediate modificationDeferred writes only after commit (REDO only); immediate writes any time (UNDO then REDO).
Clustered vs secondary indexClustered: matching records are physically together (h + r/bf). Secondary: about one I/O per record (h + r).
MySQL vs Oracle on deadlockMySQL rolls back the whole victim transaction; Oracle rolls back only the failing statement.
MySQL vs Oracle on readersMySQL default REPEATABLE READ gives a snapshot; Oracle default READ COMMITTED gives statement-level reads. Oracle has no READ UNCOMMITTED.
FOR UPDATE NOWAIT vs SKIP LOCKEDNOWAIT fails immediately; SKIP LOCKED silently ignores locked rows and returns the rest.

4.Rules & Conditions Checklist

Optimization

  • Push single-relation selections; a mixed condition goes just above the join.
  • Turn products + equality selection into joins.
  • Join the most selective pair first.
  • Push projections to keep only needed attributes.
  • Function-wrapped columns are not sargable.

Concurrency

  • Read/read never conflicts.
  • Acyclic precedence graph ⇔ conflict serializable.
  • Strict ⇒ cascadeless ⇒ recoverable.
  • S/S compatible; S/X and X/X block.
  • Lock point = end of the growing phase.
  • Deadlock ⇔ cycle in the wait-for graph.

Recovery

  • UNDO backward, REDO forward.
  • Commit before checkpoint → ignore.
  • Abort record → ignore.
  • Scan from the earliest start of a checkpoint-active transaction.
  • UNDO/REDO write absolute values (idempotent).
  • Shadow paging: lowest free location; commit frees the replaced ones.

Transactions

  • DDL commits implicitly.
  • A failed statement does not end the transaction.
  • AUTO_INCREMENT / identity values are not rolled back.
  • Re-issuing SAVEPOINT with the same name moves it.

5.Frequently Confusing Points

Traps the source flags explicitly
  1. Index nested loop is not automatically fastest. With unclustered matches it cost 301,250 against BNL's 76,250 in U3-A-07.
  2. A clustering column order matters. idx_ds(dept_id, salary) beat idx_sd(salary, dept_id) by about 10× in U3-A-09.
  3. Oracle needs IS NOT NULL before an index can serve an ordered scan on a nullable column (U3-A-15).
  4. REPEATABLE READ still shows a phantom on a locking read. The snapshot count stays 5000 while FOR SHARE returns 5001 (U3-C-20).
  5. MySQL and Oracle roll back different amounts on deadlock. Whole transaction vs single statement (U3-C-19).
  6. UNDO run forward gives the wrong value. A ends at 2 instead of 1 in U3-D-26.
  7. REDO run out of order gives the wrong value. P2 ends at 180 instead of 170 in U3-D-21.
  8. A committed transaction can still be undone indirectly. U3-D-19 shows T2's committed B derived from rolled-back A.
  9. A gap in the identity sequence is not an atomicity failure (U3-B-12).

7.Accuracy Notes & Curation Summary

Honesty note on execution (from the source audit)

The source states plainly that no MySQL or Oracle instance was available when it was written: every solution is hand-checked, and every “expected” plan, lock or log output is a description rather than a captured result. No SQL in this guide has been executed or tested here either. Run each exercise once; where an EXPLAIN or lock output differs from the description, trust your database.

What was retained

  • All four sections (A, B, C, D) with at least one worked example per distinct concept.
  • All formulas and cost models: block counts, selectivity, BNL and INL costs, access-path costs and break-even, TO/Thomas/OCC rules, recovery and checkpoint rules, shadow-paging rules.
  • The corrected U3-C-19 solution (MySQL rolls back the whole victim transaction; Oracle only the failing statement) — the source explicitly flags its earlier wording as wrong.
  • Platform-specific caveats: Oracle IS NOT NULL for ordered index scans, Oracle's FOR UPDATE + row-limiting restriction, MySQL gap locking, deadlock rollback scope, autocommit.
  • Every numbered table, recovery trace and shadow-paging snapshot for the selected questions.

What was consolidated or excluded

  • Setup scripts (u3_dept, u3_emp, u3_account, …) are not reproduced; the guide references the tables by name and states the assumed starting values instead.
  • Batch status reports, progress notes and conversational transitions from the four batches are removed.
  • Duplicate questions testing the same concept are collapsed into one worked example with a “Related” pointer to the parallel question (for example C-02 ↔ C-24, C-05 ↔ C-06 ↔ C-25, C-15 ↔ C-28, C-17 ↔ C-29, D-07/D-08/D-27).
  • The 40-question coverage matrix is summarised rather than reproduced row by row; its per-topic counts (A = 16, B = 12, C = 31, D = 27, 86 total, 30 executable) are preserved in the source.
  • Repeated expected outputs for the same pattern (for example the reset balances) are stated once.
  • Trivially similar variations that introduce no new concept were omitted, but no topic was dropped.
